# Server 韌體 CI/CD 特殊流程

> CI/CD 學習路線 第五階段

---

## 一、韌體開發的本質差異

```
純軟體 CI/CD：
  程式碼 → 編譯 → 測試 → 部署到 Server → 完成
  全程在電腦/雲端裡跑，不碰實體

韌體 CI/CD：
  程式碼 → 編譯 → 產生 .bin → 燒錄進晶片 → 實體機台測試 → 完成
                               ↑
                         這一步碰到真實硬體，
                         虛擬環境無法完全替代
```

---

## 二、韌體 CI/CD 的三個特殊問題

### 問題 1：測試環境無法完全虛擬化

```
軟體測試：
  docker run test-env → 跑完 → 刪掉
  快速、乾淨、無限複製

韌體測試：
  燒錄進實體 BMC 晶片 → 等機台開機 → 跑測試 → 看硬體反應
  慢（開機就要幾分鐘）、機台數量有限、可能燒壞
```

### 問題 2：測試時間長

```
軟體單元測試：  幾秒 ～ 幾分鐘
韌體整合測試：  幾十分鐘 ～ 幾小時（要等硬體完成各種動作）

→ CI Pipeline 設計必須考慮「快速反饋」和「完整測試」的分層
```

### 問題 3：韌體版本相依性複雜

```
一台 Server 同時有：

  ┌──────────────────────────────────────────┐
  │              一台伺服器                   │
  │                                          │
  │  UEFI/BIOS (v1.2.3)                     │
  │  BMC firmware (v2.0.1)                  │
  │  CPLD firmware (v0.5)                   │
  │  NIC firmware (v4.2.1)                  │
  │  SSD firmware (v3.1.0)                  │
  └──────────────────────────────────────────┘

  → 這五個版本必須相容，任何一個改了都可能影響其他的
  → CI/CD 要管理「版本組合」的測試矩陣
```

## 三、韌體 CI/CD Pipeline 的完整分層

```
┌────────────────────────────────────────────────────────┐
│  Level 1：靜態分析層（幾分鐘）                          │
│  → 在程式碼階段就擋掉明顯問題                           │
│  → 不需要硬體，純軟體跑                                 │
│                                                        │
│  ✓ 語法檢查（Linter）                                  │
│  ✓ 靜態程式碼分析（MISRA C / Coverity）                │
│  ✓ 安全漏洞掃描                                        │
│  ✓ 授權合規檢查（GPL / 商業授權）                      │
└────────────────────────────────────────────────────────┘
                        │ 通過
                        ▼
┌────────────────────────────────────────────────────────┐
│  Level 2：建置層（10～30 分鐘）                         │
│  → 確認程式碼能成功編譯                                 │
│  → 在 Docker Container 跑，環境一致                    │
│                                                        │
│  ✓ 交叉編譯（Cross-compile for ARM/x86）               │
│  ✓ 多版本建置（Debug / Release / 不同硬體平台）         │
│  ✓ 產生 .bin / .rom / .efi 韌體映像檔                  │
│  ✓ 建置產出物存到 Artifact Server                      │
└────────────────────────────────────────────────────────┘
                        │ 通過
                        ▼
┌────────────────────────────────────────────────────────┐
│  Level 3：模擬測試層（幾分鐘）                          │
│  → 用軟體模擬硬體行為，快速驗證基本功能                 │
│                                                        │
│  ✓ QEMU 模擬器跑部分 BIOS 邏輯                        │
│  ✓ Unit Test（pytest / CUnit）                        │
│  ✓ Mock BMC 模擬 IPMI 回應                            │
└────────────────────────────────────────────────────────┘
                        │ 通過
                        ▼
┌────────────────────────────────────────────────────────┐
│  Level 4：實體機台測試層（幾小時）                      │
│  → 真的燒錄進硬體，跑真實測試                          │
│  → 只有 PR merge 到 main 才觸發（或 Nightly Build）    │
│                                                        │
│  ✓ 燒錄韌體到測試機台                                  │
│  ✓ 開機序列驗證（POST、BIOS 初始化）                   │
│  ✓ LLT（Low Level Test）                              │
│  ✓ 電源循環壓力測試                                    │
│  ✓ 硬體感測器讀值驗證                                  │
└────────────────────────────────────────────────────────┘
                        │ 通過
                        ▼
┌────────────────────────────────────────────────────────┐
│  Level 5：系統整合測試層（幾天）                        │
│  → 最完整的驗收測試，接近真實出貨狀態                   │
│  → 通常是 Nightly / Weekly Build 才跑                  │
│                                                        │
│  ✓ 多台機器組成的叢集測試                              │
│  ✓ 韌體版本組合相容性矩陣                              │
│  ✓ 長時間穩定性測試（24h / 72h）                       │
│  ✓ OCP / UEFI 規範合規測試                             │
└────────────────────────────────────────────────────────┘
```

## 四、Test Farm 是怎麼運作的？

```
┌──────────────────────────────────────────────────────┐
│                     Test Farm                        │
│                                                      │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐           │
│  │ Server A │  │ Server B │  │ Server C │  ...       │
│  │ (測試中) │  │ (閒置)   │  │ (測試中) │           │
│  └────┬─────┘  └──────────┘  └────┬─────┘           │
│       │                           │                  │
│  ┌────┴───────────────────────────┴──────────┐       │
│  │           BMC Network / IPMI              │       │
│  │  （透過這個網路遠端控制機台電源、燒錄）    │       │
│  └────────────────────┬──────────────────────┘       │
└───────────────────────┼──────────────────────────────┘
                        │
                        ▼
              Jenkins Agent（Test Farm 管理程式）
              ・接收 Jenkins Master 的指令
              ・決定把任務派給哪台空閒機器
              ・執行燒錄、監控測試、收集結果
```

### 機台狀態管理：

```
空閒 → 被 Jenkins 預約 → 燒錄中 → 測試中 → 回報結果 → 清理 → 空閒
                                                        ↑
                                                   （清除韌體、
                                                    回到乾淨狀態
                                                    給下個 job 用）
```

## 五、韌體燒錄流程（細節）

```
Jenkins Agent 拿到任務
      │
      ▼
① 從 Artifact Server 下載 .bin 韌體映像檔
      │
      ▼
② 確認目標機台是空閒的（避免衝突）
      │
      ▼
③ 透過 BMC 網路把機台關機
   ipmitool -H <bmc-ip> power off
      │
      ▼
④ 透過 BMC 燒錄新韌體
   方式 A：BMC 本身的 update API
   方式 B：USB 模擬（虛擬 USB 掛載 .bin）
   方式 C：IPMI OEM 指令
      │
      ▼
⑤ 等待燒錄完成（幾分鐘）
      │
      ▼
⑥ 重新開機，讓新韌體生效
   ipmitool -H <bmc-ip> power on
      │
      ▼
⑦ 等機台開機完成（監控 IPMI 狀態）
   → 等 60 秒確保 BMC 就緒
      │
      ▼
⑧ 跑測試腳本
      │
      ▼
⑨ 收集結果，回報 Jenkins
      │
      ▼
⑩ 清理機台，標記為空閒
```

## 六、版本管理策略

### Artifact 命名規則

```
bmc-firmware_v2.1.0_build-1234_20240920.bin
              ↑      ↑          ↑
           版本號  Jenkins    日期
                   Build編號
```

### 版本相容性矩陣測試

```
          BIOS v1.1  BIOS v1.2  BIOS v1.3
BMC v2.0     ✅         ✅         ❌
BMC v2.1     ✅         ✅         ✅
BMC v2.2     ❌         ✅         ✅

→ CI/CD 要自動跑這個矩陣，找出不相容的組合
→ 使用 Jenkins Matrix Job 或 GitHub Actions matrix strategy
```

## 七、個人工作經驗對應

```
在緯創做的 LLT 自動化腳本
    ↓
對應到 Level 4：實體機台測試層

具體對應：
  ・ipmitool power on/off     → 機台電源控制
  ・等 60 秒確認 BMC 就緒     → 開機序列驗證
  ・分層診斷框架（POST code）  → 測試失敗時的根因分析
  ・自動循環跑測試             → 長時間壓力測試

「已熟悉 Level 4 的實際流程，
  理解如何把它接上 CI/CD 自動化。」
```

## 八、緯穎推測完整 Pipeline

```
git push（韌體程式碼）
      │
      ▼
Level 1 靜態分析（幾分鐘）
  ✓ MISRA C 檢查
  ✓ 安全掃描
      │ 通過
      ▼
Level 2 建置（15 分鐘）
  ✓ Docker Container 內交叉編譯
  ✓ 產生 bmc-v2.1.0.bin
  ✓ 上傳 Artifact Server
      │ 通過（PR 開啟）
      ▼
Level 3 模擬測試（10 分鐘）
  ✓ 單元測試
  ✓ Mock BMC 整合測試
      │ 通過
      ▼
    ← PR Merge 進 main 後才繼續 →
      │
      ▼
Level 4 實體機台 LLT（2～4 小時）
  ✓ Jenkins 預約空閒機台
  ✓ 燒錄韌體
  ✓ 開機序列驗證
  ✓ 功能測試（電源、感測器、IPMI 指令）
  ✓ 電源循環壓力測試
      │ 通過
      ▼
Level 5 系統整合（Nightly，整晚）
  ✓ 多版本相容性矩陣
  ✓ 72 小時穩定性測試
      │ 通過
      ▼
  ✅ 發佈為候選版本（Release Candidate）
```

## 本階段總結

```
韌體 CI/CD 三個核心特殊點：

1. 必須碰真實硬體
   → Test Farm + Jenkins Self-hosted Agent
   → 機台狀態管理（空閒/預約/測試中）

2. 測試時間長，要分層
   靜態分析（快）→ 建置 → 模擬 → 實體機台（慢）
   愈快的測試愈早跑，減少開發者等待時間

3. 版本相依性複雜
   → 多個韌體組件要測試相容性矩陣
   → Artifact 命名和版本追蹤要嚴格
```
