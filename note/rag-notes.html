整體 RAG 流程

這個系統是一個 RAG（Retrieval-Augmented Generation）客服機器人。使用者上傳客服文件後，系統將文件向量化存入資料庫；使用者提問時，系統找出最相關的片段，組合 prompt 交給 Claude 生成回答。

Ingestion

文件上傳與向量化

流程順序與常見誤解

正確順序：

PIPELINE
文件上傳 → Chunking → Embedding → 寫入 ChromaDB（資料庫自動建索引）
常見誤解
「索引」不是獨立步驟，是 ChromaDB 在呼叫 collection.add() 時自動在內部建立的，不需要手動觸發。

語意切割 — _semantic_chunk()

程式碼位置：app/core/rag/ingestion.py:18

與傳統字數切割的根本差異：字數切割不管內容，切到字數上限就截斷；語意切割以原文的段落結構為主要依據，字數只是兜底。

兩段式邏輯

Python — ingestion.py
def _semantic_chunk(text: str) -> list[str]:
    max_size = 500   # chunk_size
    min_paragraph = 80

    # 第一段：按空行切段落（尊重原作者的語意邊界）
    raw_paragraphs = [p.strip() for p in text.split("\n\n") if p.strip()]

    # 第二段：合併太短的段落，保留適中的段落
    for para in raw_paragraphs:
        if len(buffer) < min_paragraph and ...:
            buffer = buffer + "\n\n" + para  # 合併太短（< 80字）
        ...

    # 太長（> 500字）交給 RecursiveCharacterTextSplitter 細切
    if len(para) > max_size:
        final_chunks.extend(splitter.split_text(para))
情況處理方式
段落 < 80 字合併到下一個段落，避免資訊量太少
段落 80~500 字直接保留，不再處理
段落 > 500 字交給 RecursiveCharacterTextSplitter 細切

RecursiveCharacterTextSplitter 的運作方式

「Recursive（遞迴）」是關鍵字。它有一個優先順序分隔符號清單，依序嘗試：

分隔符號優先順序
["\n\n", "\n", "。", "！", "？", " ", ""]

運作邏輯：先試能不能在空行切？可以就切。不行，退而求其次在換行切。還是不行，在句號切。最後實在沒辦法，才硬切字元。

chunk_overlap=50 的作用
每個 chunk 的結尾與下一個 chunk 的開頭重疊 50 個字，避免跨 chunk 邊界的語意被硬切斷，讓內容在邊界處保有連貫性。

Embedding 模型

使用模型：sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2

工具套件：fastembed（本地執行，不需要網路）

淺白說明：把文字翻譯成 384 個數字組成的座標。語意相近的兩段文字，在這個 384 維空間裡的點距離很近；語意無關的文字距離很遠。查詢時用數學計算（cosine 相似度）找出最相關的 chunk。

模型名稱拆解

部分意思
sentence-transformers專門把句子轉成向量的框架
paraphrase訓練時用「同義改寫句對」學習，相同意思但不同說法的句子向量靠近
multilingual支援 50+ 語言，中英文同一個意思，向量也會很接近
MiniLMMicrosoft 開發的輕量架構，大模型「蒸餾」成小模型，速度快但效果接近
L12有 12 層神經網路
v2第二版

與其他模型比較

比較對象差異
OpenAI text-embedding-3-small需付費打 API、需要網路；本模型完全本地，免費
all-MiniLM-L6-v2（英文版）只擅長英文；本模型支援中文
更大的模型（L24、L32）向量品質稍高但慢很多、佔記憶體多；文件量小的專案 L12 足夠

ChromaDB — 向量資料庫

普通資料庫 vs 向量資料庫

普通資料庫（MySQL）向量資料庫（ChromaDB）
搜尋問題「哪筆欄位等於某個值？」「哪幾筆向量和查詢向量最接近？」
搜尋方式精確比對近似最近鄰搜尋（ANN）

MySQL 做不到向量近似搜尋，因為沒辦法有效率地在幾千個 384 維向量裡找「最接近的」。

ChromaDB 在本專案的儲存方式

Python — vectorstore.py:17
chromadb.PersistentClient(path=str(settings.chroma_dir))

PersistentClient 代表資料直接存成本機的資料夾和檔案（SQLite + 二進位檔）。collection.add() 是直接寫檔，collection.query() 是直接讀檔，完全不走網路。

HNSW 索引

程式碼設定 "hnsw:space": "cosine"，表示使用 cosine 距離的 HNSW 圖索引。在你 add() 資料時，ChromaDB 自動建立這個圖結構，讓後續查詢不需要全部比對。（詳見 Retrieval 階段的說明）

為什麼選 ChromaDB

選項適合場景
ChromaDB（本專案）本地開發、side project、快速上手，零設定
Pinecone雲端、大規模生產環境，需付費
Weaviate / Qdrant需要 Docker 或 Server，設定複雜，適合團隊協作
pgvector已有 PostgreSQL 系統想順便加向量搜尋

寫入向量資料庫的資料結構

每一筆資料（每個 chunk）由四個欄位組成，對應 ingestion.py:73 的 collection.add()：

欄位型態內容範例
idsstring付款方式說明.pdf_chunk_0
documentsstringchunk 的原始文字
embeddingslist[float][0.023, -0.15, ...] 共 384 個數字

重點
原文和向量都存進去。查詢時用向量找最相關的 chunk，找到後把原文傳給 LLM 生成答案。
Retrieval

語意搜尋與過濾

流程總覽與常見誤解糾正

FLOW
使用者問題
  → embed()（與 Ingestion 同一個模型）
  → 查詢向量
  → collection.query()（HNSW，不是全比對）
  → 取前 5 個最近鄰 + 它們的距離
  → similarity = 1 - distance，過濾 < 0.3 的
  → 剩下的 chunk（0~5 個）
  → 組合 prompt 給 Claude
常見誤解
不是同時做「取出相似度 > 0.3 的前 5 個」，而是兩步：
1. 先取前 5 個最相似的（不管分數）
2. 再用 0.3 門檻過濾，分數不夠的丟掉

最終可能是 5、3、1 個，甚至 0 個。0 個時直接回覆拒答字串，不呼叫 Claude。
Python — retrieval.py
# 步驟一：先取 top 5（不管分數）
results = collection.query(
    query_embeddings=[query_embedding],
    n_results=settings.retrieval_top_k,  # = 5
    include=["documents", "metadatas", "distances"],
)

# 步驟二：過濾相似度 < 0.3 的
for doc, meta, distance in zip(documents, metadatas, distances):
    similarity = 1 - distance
    if similarity >= settings.similarity_threshold:  # 0.3
        filtered_chunks.append(doc)

為什麼必須用同一個 Embedding 模型

Retrieval 階段呼叫的是完全相同的 embed() 函式（來自 vectorstore.py），使用同一個模型 paraphrase-multilingual-MiniLM-L12-v2。

原因
不同模型產生的向量，座標系統不同，比出來的距離毫無意義。就像台灣用 TWD97 座標系、歐洲用 WGS84，直接比數字不能代表真實距離。存進去用什麼模型轉，查詢時就必須用同一個模型轉。

HNSW vs 暴力搜尋

暴力做法（Brute Force）

CONCEPT
查詢向量 → 跟第1筆比 → 跟第2筆比 → ... → 跟第N筆比 → 取最近
複雜度：O(N)　資料越多越慢

HNSW 的做法

在 add() 時預先把所有向量建成多層圖結構：

HNSW 圖結構
第 3 層（稀疏）：少數節點，長程連線 → 快速定位大概區域
第 2 層：       節點變多
第 1 層（密集）：所有節點，短程連線 → 精細搜尋

查詢策略：從稀疏層進入 → 逐層下降 → 在密集層精細搜尋。類比：在台灣找人，不逐戶敲門，而是先縮到縣市 → 區 → 街 → 再逐戶找。

複雜度從 O(N) 降到接近 O(log N)，資料量十倍，搜尋時間只多一點點。

近似最近鄰（ANN）
HNSW 是近似搜尋，理論上可能找不到數學意義上絕對最近的那幾個，但準確率通常 > 95%。語意搜尋本身就不需要「數學上絕對最近」，「夠近、夠相關」就夠了。

距離轉相似度換算

ChromaDB 回傳的是距離（distance），程式碼在 retrieval.py:42 轉換：

Python

similarity 範圍意義
接近 1非常相似
接近 0不相關
負數語意相反
Generator

Prompt 組合與生成回答

Generator 接收 Retrieval 的結果，負責「組合 prompt → 呼叫 Claude API → 回傳答案」。組合 prompt 是在 Generator 階段，不是 Retrieval。

found=False 的提前返回

Python — generator.py:45
if not retrieval.found:
    return {
        "answer": "根據現有文件，我無法回答這個問題。",
        "sources": [],
        "confidence": "no_context",
    }

當 Retrieval 找不到任何超過 0.3 門檻的 chunk 時，直接回傳固定字串，完全不呼叫 Claude API。

設計原因
省錢：沒有上下文的情況下叫 Claude 回答，只會得到幻覺（hallucination），不如不叫。
準確：固定拒答字串比 Claude 在沒有依據時亂猜，對使用者更誠實、更可靠。

System Prompt 完整內容

SYSTEM PROMPT
你是一個專業的客服助理。
你只能根據下方【參考文件】的內容來回答使用者的問題。

規則：
1. 只使用【參考文件】中提供的資訊作答
2. 如果文件內容不足以回答問題，請明確回覆：「根據現有文件，我無法回答這個問題。」

Temperature 與 Top_p 參數

本專案的問題
目前呼叫 Claude 時沒有設定 temperature，使用預設值（= 1）。對客服 QA 場景來說太高，可能導致同一個問題問兩次得到不同回答。

什麼是 Temperature

控制模型「有多隨機」。模型在生成每個字之前，會對所有可能的下一個字算出機率分佈，temperature 決定這個分佈有多平：

Temperature效果
接近 0幾乎每次都選機率最高的字，輸出非常穩定、可預測
1（預設）按照原始機率選，有適度的多樣性
接近 2機率分佈被拉平，更隨機、更有創意，但也更容易亂

什麼是 Top_p

另一種控制隨機的方式：只從累積機率達到 p 的那些字裡面選，其他直接排除。
通常只調 temperature 或 top_p 其中一個，同時調會讓效果難以預測。

不同場景的建議

場景建議值
客服 QA（本專案）0 ~ 0.1
文件摘要0 ~ 0.3
程式碼生成0 ~ 0.2
行銷文案0.7 ~ 1
故事創作1 ~ 1.5
