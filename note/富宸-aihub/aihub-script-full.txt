=== 節點 1：開場 ===

【動作】打開 AI Hub 網頁，確認左側管線停留在「開場」節點（預設即是）。
        視需要切換到深色主題（左下角切換按鈕），讓螢幕對觀眾更清晰。

大家好，今天我要和大家分享的是我在富宸材料負責開發的一套系統，叫做 AI Hub。

先講一個很實際的痛點。富宸材料是一家有幾百名員工的製造業公司，公司的知識分散在四個系統裡：

第一個是 KMS，知識管理平台，裡面有員工自己寫的 SOP、公司規章、部門作業辦法。
第二個是 DCC，文件控制系統，專門管受控文件，像是材料規格書、工程圖紙、版本管制的技術文件。DCC 裡的文件有嚴格的版本號，同一份文件可能有 R1、R2、R3 好幾個版本。
第三個是 BPM，簽核流程系統，裡面有每個人在走的審核案件，請假單、採購申請、報帳記錄，都在這裡。
第四個是 HR，員工資料表，每個人的姓名、職稱、部門、負責的業務範圍。

以前要查這些東西，要分別登入四個不同的系統。新進員工要問「請假要找誰審？」，可能要先登入 HR 查到部門主管，再去 BPM 看流程，再去 KMS 找請假辦法。這個過程完全依賴「問同事」，沒有辦法快速、系統化地取得答案。

【動作】用手指向右側內容區「四個知識來源」的卡片區塊。

AI Hub 的目標就是讓員工用自然語言，一句話就能跨系統查詢這些知識。

技術棧這邊快速帶一下。線上推理用的是 Gemini 2.5 Flash，這個模型推理速度快，適合即時串流；文件離線分段用的是 Kimi-k2.5，它有 256K 的 context window，可以一次讀完整份文件再切；知識庫搜尋用 PostgreSQL + pg_trgm 延伸模組做字面匹配；使用者記憶搜尋才用 pgvector 做向量搜尋；快取用 Redis 兩層架構。

為什麼技術棧這樣組合？這正是今天我要詳細說的，每一個選擇背後都有具體的設計考量。

【→ 銜接到節點 2】

在進入 AI Hub 的架構之前，我想先花一點時間回顧基礎 RAG 是什麼，因為 AI Hub 的每一個設計決策，都是在解決基礎 RAG 的某個限制。如果你已經很熟悉 RAG，這段可以當作對比的基準線。


=== 節點 2：基礎 RAG 對比 ===

【動作】點擊左側管線的「基礎 RAG 對比」節點，等右側內容切換完成。
        指向右側「基礎 RAG」那一欄的虛擬程式碼區塊。

RAG，Retrieval-Augmented Generation，增強式檢索生成，是目前最主流的企業知識庫 AI 方案。它的基本流程是這樣：

第一步，把所有文件切成 chunk，通常是固定 500 到 1000 個 token 切一段。
第二步，把每個 chunk 用 Embedding 模型轉成向量，存進向量資料庫，比如 Chroma 或 Weaviate。
第三步，使用者問一個問題，把這個問題也轉成向量。
第四步，在向量資料庫裡做 cosine similarity 搜尋，找最相近的前 K 個 chunk。
第五步，把這些 chunk 塞進 LLM 的 context，讓 LLM 生成回覆。

這個架構很直覺，而且對很多場景確實夠用。但是放到企業知識庫的場景，它有幾個很具體的問題。

第一個問題：固定切割破壞語意。

想像一份請假辦法，共 10 頁，裡面有「申請資格」、「簽核流程」、「特殊假別說明」三個章節。如果你每 500 個 token 切一刀，很可能第一個 chunk 是「申請資格的後半段 + 簽核流程的前半段」，這個 chunk 單獨拿出來，任何人看了都會很困惑，LLM 也一樣。LLM 拿到殘缺的段落，要回答準確的問題，難度非常高。

第二個問題：全量向量搜尋，搜尋範圍沒有縮小。

基礎 RAG 不管你問的是什麼，都要對整個向量資料庫做相似度計算。公司有幾百份文件，每份文件切了幾十個 chunk，乘起來可能有幾萬個向量。每次搜尋都要比對幾萬個向量，而且向量搜尋是近似搜尋，不是精確搜尋，容易把不相關的 chunk 也撈進來。

第三個問題：單次生成，LLM 沒有辦法補充資訊。

基礎 RAG 是一次性的：撈出 chunk，塞進 context，LLM 生成。如果 LLM 發現撈到的 chunk 不夠回答問題，它也只能基於現有的資訊生成，無法主動說「我需要再查一下」。

第四個問題：沒有使用者記憶。

基礎 RAG 每次對話都是全新的開始，LLM 不知道你是誰、你的職位是什麼、你上次問了什麼。對企業員工來說，這讓系統顯得很「冷」，每次都要重新解釋背景。

【動作】指向右側「AI Hub（強化版）」那一欄的管線圖，逐行說明。

AI Hub 最重要的一個設計決策，是把管線分成兩條線：離線採編和線上查詢。

離線的部分，只在文件上傳的時候執行一次，不管之後有多少人查詢，這個成本不重複。
線上的部分，每次使用者提問時才觸發，但因為離線已經做好了前處理，線上可以走更快的路。

這個分離是後面所有優化的基礎。我們把計算密集的工作放到離線，把結果存好，讓線上查詢可以直接取用。

【動作】指向「五段式管線」的 ASCII 圖，從上到下逐行指著說。

五段式管線的全貌是這樣：Stage 01 是文件採編，離線執行；Stage 02 是意圖分類，Stage 03 是混合檢索，Stage 04 是 context 組裝，Stage 05 是生成和快取寫回，這四個都是線上的。

接下來我們一個一個看。

【→ 銜接到節點 3】

先從離線的部分開始。Stage 01 是整個系統的資料基礎，它做得好不好，直接決定後面的搜尋品質。


=== 節點 3：Stage 01 文件採編 ===

【動作】點擊左側管線的「Stage 01 文件採編」節點，等右側內容切換。
        注意左側節點旁的「OFFLINE」標籤，可以口頭提示聽眾。

這個 Stage 有一個橘色的 OFFLINE 標籤，意思是它只在文件上傳時執行一次，不是每次查詢都跑。

先說 LibrarianAgent 的觸發流程。當有人把一份文件上傳到 KMS 或 DCC 時，系統會把這個任務丟進 AWS SQS 的訊息佇列，LibrarianAgent 是一個獨立的 worker，它監聽這個 queue，拿到任務之後，先從 S3 把檔案下載下來，然後根據來源類型決定怎麼處理。

【動作】指向右側「四種來源的採編策略」表格，逐行說明。

四種來源有不同的策略。KMS 的文章通常本來就有 Markdown 格式，結構清楚，整篇當一個 Segment 就夠了。DCC 的 PDF 技術文件才是需要 LLM 幫忙分段的，因為 PDF 沒有明確的語意邊界。BPM 和 HR 是結構化資料，JSON 或資料庫記錄，整份當一個 Segment 也夠用。

DCC 技術文件是最複雜的，我重點說這個。

【動作】指向左右欄的「固定切割 vs 語意切割」對比區塊。

想像這樣一個場景：一份「請假辦法」，5 頁的 PDF。如果用固定切割，每 500 個 token 切一刀，你可能得到這樣的第一個 chunk：

「...第二條 凡在職員工均可申請，惟需提前三天以上...」

這個 chunk 從第二條的中間開始，不知道前面是什麼，也不知道後面在講什麼。

AI Hub 把整份文件餵給 Kimi-k2.5。Kimi 有 256K 的 context window，5 頁 PDF 根本不是問題，它可以讀完整份文件再決定怎麼切。Kimi 的分析結果是結構化 JSON，每個 Segment 有完整的標題、章節資訊和內容，而且每段在語意上是獨立的，可以單獨理解。

【動作】指向 Kimi-k2.5 輸出的 JSON 程式碼區塊，逐欄說明。

輸出格式裡，title 是這個 Segment 的標題路徑，例如「請假申請 > 簽核流程」，這讓後續的 title_score 評分有意義；content 是完整的段落文字；chapter 是這段屬於哪個章節；sequence 是在文件中的順序。這些欄位每一個都在後面的搜尋評分裡用到。

接下來說 Taxonomy 分類。

每個 Segment 採編完之後，LLM 會自動把它掛到對應的分類節點。比如「請假申請簽核流程說明」會被掛到 tx_hr_leave 這個節點，「BPM 系統操作指引」會被掛到 tx_bpm_workflow。

為什麼選 LLM 自動分類而不是人工維護？因為公司的業務在演化，文件類型會越來越多。如果分類樹由人工維護，每增加一類都要改程式碼。AI Hub 的設計是：如果 LLM 找不到合適的現有分類節點，它可以建議新增一個節點，Taxonomy 隨著業務自動成長。

最後是 PII 脫敏。DCC 文件裡可能有員工的個人資料，比如身份證號、手機號碼。採編階段就把這些資料替換掉，確保它們不會進入知識庫，讓後來查詢的人看到不該看到的資訊。這是一個安全設計，而且比事後過濾容易多了。

【動作】停頓一秒，讓聽眾消化。

這個 Stage 的核心思維是：在文件上傳的時候多花一點計算資源，把資料前處理做好，讓後面的線上查詢可以更快、更準。一次投資，多次受益。

好，文件已經採編好了，存進了 PostgreSQL。接下來使用者問了一個問題，系統要怎麼處理？這是 Stage 02 和 Stage 03 的工作。


=== 節點 4：Stage 02+03 意圖路由 + 混合檢索 ===

【動作】點擊左側管線的「Stage 02+03 意圖路由 + 混合檢索」節點。
        左側節點旁會出現「ONLINE」標籤，代表每次查詢都觸發。

使用者送出一個問題，第一步不是馬上去搜知識庫，而是先問：這個問題是什麼性質的？

【動作】指向右側「4-way 意圖路由」表格，逐行說明。

AI Hub 把所有問題分成四類。

第一類是 CHITCHAT，就是打招呼、閒聊。「你好呀」、「今天天氣很熱」。這種問題不需要查任何資料，直接回覆就好。如果讓它去跑完整的 RAG 流程，不只慢，還浪費 token。

第二類是 SKILL_ACTION，就是指令性操作。「幫我換大頭照」、「改一下我的暱稱」。這類問題的答案不在知識庫裡，而是要呼叫特定的工具函式。

第三類是 PEOPLE_FINDER，找人。「冷氣壞了要找誰？」、「採購流程要找哪個部門？」這類問題可以走一條比較短的 Expert Search 路徑，不需要跑全量的知識庫搜尋。

第四類才是 KNOWLEDGE_QA，知識問答。「請假要怎麼申請？」、「BPM 的審核流程是什麼？」這類問題才走完整的 RAG 管線，最多執行 5 個步驟。

這個分流的設計讓系統非常有效率。80% 的問題可能根本不需要走完整的 RAG。

接下來說 generateObject，這是 Stage 02 最有趣的設計。

【動作】指向右側「generateObject」程式碼區塊，逐欄說明。

傳統的做法是：先呼叫 LLM 做意圖分類，再呼叫 LLM 提取關鍵字，再呼叫 LLM 生成一個即時的回饋訊息給使用者。這樣要 3 到 4 次 LLM 呼叫，延遲加起來很可觀。

AI Hub 用 Vercel AI SDK 的 generateObject，配合 Zod Schema 定義好輸出格式，一次呼叫就拿到 6 個欄位。

第一個欄位 intent，是分類結果，同時還帶了括號，括號裡是 LLM 建議要載入的 Skill 名稱。例如 "KNOWLEDGE_QA (ai-hub-bpm)" 的意思是：這是知識問答，而且應該額外載入 BPM 相關的 Skill。

第二個欄位 taxonomyIds，是分類標籤清單，例如 ["tx_bpm_approval", "tx_hr_leave"]。這個清單直接用在 SQL 的 WHERE 條件裡，縮小搜尋範圍。

第三個欄位 keywords，是關鍵字清單，用於 pg_trgm 搜尋，同時也是 L1 cache 的 key 的一部分。

第四個欄位 mandatoryKeywords，是必須出現的詞。如果一個 Segment 裡沒有這個詞，就算其他分數再高，也不會被納入結果。

第五個欄位 expertSearchKeywords，是搜人的關鍵字。它和 keywords 是不同的，因為搜人和搜文件的關鍵字語氣不一樣。

第六個欄位 acknowledgment，是一個簡短的即時回饋，「讓我幫您查詢請假相關的資料」，這個字串會立刻串流給前端顯示，讓使用者知道系統已經在處理了，不用乾等。

【→ 說明搜尋機制】

現在我要說 Stage 03，混合檢索，這是最反直覺的部分。

【動作】指向「混合檢索 — 刻意不用向量搜尋 Segment」區塊。

AI Hub 在知識庫搜尋這一塊，刻意沒有用向量搜尋。Segment 在建立的時候，沒有做 Embedding，資料庫裡只存文字。

為什麼？因為我們的場景是企業內部知識庫，使用者問的問題和文件裡的用詞通常高度重疊。「請假怎麼辦理」和文件裡的「請假申請說明」，字面上就已經很接近了，用字面匹配就夠用，而且更快、更可控。

向量搜尋解決的問題是語意橋接，例如使用者說「出差費用怎麼報」，文件裡寫「差旅報帳流程」，這時候字面不同但語意相近，才需要向量。但在 AI Hub 的情境裡，這種落差比較少，所以 pgvector 只用在「使用者記憶」那一塊，稍後再說。

【動作】指向「pg_trgm 兩層機制」的左右欄比較區塊。

pg_trgm 是 PostgreSQL 的一個延伸模組，它把每個詞拆成三個字元的組合（三元組），然後計算兩段文字的三元組重疊比例，來判斷相似度。

兩層機制這樣運作：

第一層是 WHERE 過濾，用 similarity() 函式加一個最低門檻，比如 0.1，同時加入 taxonomy_id IN (...) 的條件，這樣就從全部幾萬個 Segment 縮小到幾百個候選。這一步的重點是速度，要快速排除明顯不相關的結果。

第二層是多維評分排名，對這幾百個候選做細緻的評分。評分有五個維度：

sim_score 是 pg_trgm 的整體相似度分數，這是基礎分。
title_score 是標題相似度，加了 ×2 的權重，因為如果標題就直接命中，這個 Segment 大概率非常相關。
kw_score 是關鍵字出現次數，一個文件裡提到「請假」越多次，越相關。
mandatory_score 是必中詞加分，如果 mandatoryKeywords 裡的詞全都出現了，才給這個加分，有一個缺失就不給。這是一個「全中才算數」的設計。
keyword_match_count 是命中了幾個不同的關鍵字，鼓勵覆蓋面廣的 Segment。

五個維度加起來排名，取前 20 個，這就是最終送給 LLM 的知識庫段落。

同時，Expert 搜尋在另一條線並行執行，用 Promise.all，不互相等待，縮短整體回應時間。

搜到的結果回來了，現在要把它們組裝成 LLM 需要的格式，然後生成回覆。這是 Stage 04 和 Stage 05 的工作，也是設計細節最多的部分。


=== 節點 5：Stage 04+05 增強生成 ===

【動作】點擊左側管線的「Stage 04+05 增強生成」節點。
        指向右側的「Context 管理 — 三個機制」卡片區塊。

Stage 04+05 我分三個主題說：Context 管理、Skill 系統、記憶與快取。

先說 Context 管理。Context 管理是 AI Hub 裡我最想強調的設計哲學：LLM 的 context window 是很珍貴的，什麼東西放進去、什麼不放，直接決定了回答的品質。

三個機制。

第一個是歷史注入。

前端設計成無狀態，每次使用者送出訊息，只送那一則最新的訊息，不送歷史。這是為了讓前端保持簡單，不用管理對話狀態。但後端需要讓 LLM 知道對話的上下文，所以後端在接到請求的時候，會去資料庫把這個使用者最近 10 筆訊息撈出來，注入到 messages 陣列的最前面，再傳給 LLM。

為什麼是 10 筆？這是一個工程上的取捨。太多的話 context 會太長；太少的話 LLM 沒有足夠的對話背景。10 筆在大多數場景下夠用，而且 token 消耗在可接受範圍內。

第二個是 pruneMessages。

當對話進行了很多輪，context 就很長。傳入 LLM 之前，先做一次壓縮。保留的是：所有的推理步驟記錄，和所有的工具呼叫記錄（function calls）。丟掉的是：重複的、冗餘的中間 assistant 訊息。這樣 context 的大小相對穩定，不會隨對話輪數線性增長。

第三個是 [internal] / [public] 雙頻道。

【動作】指向「[internal]/[public]」的程式碼區塊。

這個設計是我覺得最精巧的部分。LLM 生成的時候，被要求用兩個標籤來分開輸出：[internal] 裡面寫推理過程，[public] 裡面才是真正給使用者看的答案。

好處有兩個。第一個是即時：[public] 的內容可以直接串流給前端顯示，不用等 [internal] 結束。第二個是 context 乾淨：資料庫只存 [public] 的部分，下一輪對話裡注入的歷史是乾淨的最終答案，不帶推理的噪聲。如果把推理也存進去，下次對話的 context 裡就有大量的中間思考，浪費 token 而且干擾 LLM。

接下來說 Skill 系統。

【動作】指向「Skill 系統 — 動態組裝 System Prompt」的表格。

System Prompt 不是一個寫死的字串，它由三層邏輯動態組裝。

第一層是 manifest 基礎。每個意圖類型對應到一組預設的 Skill 清單，這是寫在 manifest 設定裡的。比如 KNOWLEDGE_QA 預設載入 knowledge-retrieval 和 reading-planner 這兩個 Skill。

第二層是 LLM 括號建議。這是一個很聰明的設計。generateObject 回傳的 intent 欄位，可以在括號裡帶一個 Skill 名稱，例如 "KNOWLEDGE_QA (ai-hub-bpm)"。系統拿到這個字串，解析出括號裡的名稱，額外載入 ai-hub-bpm 這個 Skill。等於是 LLM 在分析問題的同時，順手說「這個問題應該要用 BPM 相關的 Skill」。

第三層是關鍵字觸發。每個 Skill 在 manifest.json 裡可以定義 triggers，例如「如果 query 裡含有『請假』、『年假』、『病假』，就觸發 ai-hub-hr-specialist」。這讓特定領域的 Skill 在最需要的時候才出現。

三層疊加的結果，就是每次查詢的 System Prompt 都是根據這次的問題動態組裝的，而不是一個靜態的大字串。

接下來說最小工具暴露。

每個 Skill 在 YAML Frontmatter 裡宣告它需要的工具清單。最終傳給 LLM 的工具集，是本次載入的所有 Skill 的工具清單聯集。換句話說，LLM 看不到這次不需要的工具。

為什麼這樣做？因為 LLM 在有很多工具的情況下，容易產生幻覺，誤呼叫不該呼叫的工具。如果 LLM 本來就看不到那個工具，它就不會去呼叫。工具越少，LLM 的決策空間越小，錯誤率越低。

【動作】指向 streamText 的程式碼區塊，說明 stopWhen。

Multi-step Agentic Loop 的設計是：LLM 自主決定要不要呼叫工具、呼叫哪個工具、用工具的結果再做什麼判斷。這個循環最多跑 5 個步驟，由 stopWhen: stepCountIs(5) 控制。

為什麼要有上限？防止無限迴圈。LLM 理論上可能一直呼叫工具、一直不確定，設一個上限是安全閥。5 步在大多數場景下夠用：查知識庫、看結果、再補查一筆、整合、生成，大概就是這樣。

接下來說記憶系統。

AI Hub 的記憶有三種，要分清楚：

第一種是 session 歷史，就是當前對話的訊息列表，前面說的「注入最近 10 筆」就是這個，存在 ai_hub_message 資料表。
第二種是使用者事實記憶，是 LLM 在對話中學到的關於你的事，例如「你的主管是 Amy」、「你偏好簡短的回覆」。這些事實被轉成向量存在 ai_hub_memory 資料表，下次新 session 還能取用。
第三種是靜態偏好，存在 ai_hub_memory 的靜態欄位，不需要語意搜尋。

pgvector 只用在第二種，因為使用者事實是短句，和當前問題的字面不一定相同，需要語意橋接才能找到相關的記憶。

當 LLM 在對話中覺得某件事值得記住，它會呼叫 save_user_memory 工具，觸發向量化和儲存。下次同一個使用者開新 session，系統會先做記憶搜尋，找到相關的事實，注入到 System Prompt 的「悄悄話」區塊。

【動作】指向「L1 / L2 雙層 Redis 快取」表格。

最後是快取，這是省成本最大的設計。

L1 cache 存的是「關鍵字組合 → 對應的 Segment ID 清單」。如果兩個人問了語意類似的問題，關鍵字組合一樣，L1 cache 命中，直接跳過 PostgreSQL 查詢，省掉 DB 時間。TTL 是 4 小時。

L2 cache 存的是最終的 LLM 回覆文字。如果完全相同的問題、相同的可讀文件集合，L2 cache 命中，直接回傳快取答案，完全跳過 LLM 生成，省掉最大的一塊成本。TTL 是 24 小時。

L2 cache 的 key 設計裡含有 userId，確保不同使用者（可能有不同的文件存取權限）不會共用同一個快取答案，不然可能出現越權問題。

Q：為什麼 Segment 不做 Embedding？向量搜尋不是更準嗎？
A：在企業內部知識庫的場景，使用者的問題和文件的用詞高度重疊，字面匹配（pg_trgm）
   的精準度已經夠用，而且評分函式可以精細調整，比向量搜尋更可控。向量搜尋用在
   使用者記憶那塊，因為那邊才有「字面不同但語意相近」的問題。

Q：Taxonomy 分類如果分類錯誤怎麼辦？
A：pg_trgm 的第一層過濾門檻（similarity > 0.1）設得很低，確保不會因為分類不完美
   就完全撈不到結果。分類主要是縮小範圍、加速搜尋，不是唯一的過濾條件。

Q：使用者記憶的隱私問題怎麼處理？
A：記憶是使用者 ID 綁定的，只有本人能讀，其他人的查詢不會觸發你的記憶。
   使用者也可以透過介面查看和刪除記憶。

Q：Multi-step 最多 5 步，如果問題需要更多步怎麼辦？
A：5 步的上限是安全閥，不是功能限制。如果 5 步真的不夠，代表這個問題的複雜度
   超出了 AI Hub 的設計範疇，應該由人工處理。在實測中，絕大多數的 KNOWLEDGE_QA
   問題在 2 到 3 步內就能完成。

Q：L2 cache 如果文件更新了，快取會過期嗎？
A：cache key 裡含有一個 version 號，文件有更新時 version 號會遞增，舊的 cache
   自然就不會被命中，等 TTL 自然過期或直接清除即可。
